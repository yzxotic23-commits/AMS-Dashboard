h2. 3. What is AMS?

AMS (Account Management System) is the dashboard used to manage WhatsApp
accounts end-to-end:

* Register number
* Activate / link WhatsApp
* Nurture account
* Deliver to business (ticket)
* Track Device, SIM, and IP
* Monitor health, bans, and recovery

FeedFlow (WSAF) is the WhatsApp engine. AMS talks to FeedFlow for QR/pairing,
session status, proxy, and feeding audit.

h2. 6. Where code lives (AMS-Dashboard)

You only need to know these folders:

| Folder / file | Meaning |
| apps/web/ | Website (UI) |
| apps/web/src/pages/ | Each screen (Register, Tickets, etc.) |
| apps/web/src/App.jsx | Website routes |
| apps/api/ | Backend API |
| apps/api/src/modules/ | API features (accounts, tickets, bridge...) |
| apps/api/src/lib/stateMachine.js | Account status rules |
| apps/api/src/lib/wsafBridge.js | Connection to FeedFlow |
| apps/api/src/lib/resourceBindings.js | Device / SIM / IP binding |
| api/index.mjs | Entry for Vercel API |
| supabase/migrations/ | Database structure |
| scripts/ | Maintenance scripts |
| .env.example | List of required settings (names only) |

Rule of thumb:

* UI change → apps/web/
* Business rule / API change → apps/api/
* Database change → new file in supabase/migrations/

h2. 7. How to run locally (first time)

# Clone AMS-Dashboard
# Copy .env.example to .env and fill values from the secrets vault (ask admin)
# Run database migrations in Supabase (files 001 to 008, in order)
# npm install
# npm run setup:supabase
# npm run create:admin
# npm run dev
# Open http://localhost:3000
# Check API: http://localhost:4000/api/v1/health

Important env names (do not put real values in Confluence):

Website:
* VITE_DEMO_MODE
* VITE_SUPABASE_URL
* VITE_SUPABASE_ANON_KEY
* VITE_WSAF_BRIDGE_URL

API:
* SUPABASE_URL
* SUPABASE_ANON_KEY
* SUPABASE_SERVICE_ROLE_KEY
* WSAF_BRIDGE_URL
* WSAF_AUTO_START

Production note:
* On Vercel, set WSAF_AUTO_START=false
* Point WSAF_BRIDGE_URL and VITE_WSAF_BRIDGE_URL to Railway FeedFlow URL

h2. 9. Account lifecycle (most important business rule)

Every account has one status.

| Status | Meaning |
| REGISTERING | Being registered |
| NURTURING | Warming up |
| AVAILABLE | Standby, ready for business |
| IN_USE | Used by business |
| LOGGED_OUT | WhatsApp disconnected |
| BANNED | Banned |
| RECOVERING | In recovery |
| RECYCLED | Closed forever |

Allowed moves only:

| From | Can move to |
| REGISTERING | NURTURING, RECYCLED |
| NURTURING | AVAILABLE, BANNED, RECYCLED |
| AVAILABLE | IN_USE, NURTURING, RECYCLED |
| IN_USE | LOGGED_OUT, BANNED, AVAILABLE |
| LOGGED_OUT | NURTURING, RECOVERING, RECYCLED |
| BANNED | RECOVERING, RECYCLED |
| RECOVERING | NURTURING, AVAILABLE, RECYCLED |
| RECYCLED | none |

Code that controls this:
* apps/api/src/lib/stateMachine.js

If you change lifecycle rules, update this file first, then UI labels, then test.

h2. 10. Resource rules (Device / SIM / IP)

| Resource | Rule |
| Device | Max 2 accounts (WS Normal + WS Business) |
| IP | Max 2 accounts |
| SIM | Linked after successful registration |
| Account | Has 1 device + 1 SIM + 1 IP |

Normal flow:

# Register number (with device + IP)
# Activate: complete checklist + link WhatsApp
# Nurture until ready
# Create ticket → review IP/proxy → go live → IN_USE

h2. 13. FeedFlow connection

AMS does not host WhatsApp itself. It calls FeedFlow.

| Direction | What is synced |
| AMS → FeedFlow | Account label, proxy, start/stop feeding |
| FeedFlow → AMS | Online/offline, feeding audit (Active / Restrict / Banned) |

Important production rule:

* After Railway redeploy, WhatsApp auth may still exist on volume
* Operator must still *manually reconnect* slots to bring them online

If AMS cannot reach FeedFlow:

# Open FeedFlow health URL
# Check WSAF_BRIDGE_URL on Vercel
# Redeploy AMS if URL changed
# Reconnect WhatsApp slots

h2. 14. Deploy guide (short)

h3. AMS (Vercel)

# Push code to AMS-Dashboard main
# Vercel auto-builds from vercel.json
# Confirm env vars are set
# Test login + /api/v1/health

h3. FeedFlow (Railway)

# Deploy WSAF-BO
# Keep volume mounted at /app/data
# Set AMS_FRAME_ORIGINS to AMS website URL
# Copy public Railway URL into AMS bridge env vars
# Reconnect WhatsApp after deploy

h2. 15. How to change the system (new Owner playbook)

h3. Change a screen

# Edit file in apps/web/src/pages/
# Route is in apps/web/src/App.jsx
# Menu is in apps/web/src/components/AppSidebar.jsx

h3. Change API / business logic

# Edit apps/api/src/modules/.../routes.js
# For status rules: edit stateMachine.js
# For Device/SIM/IP binding: edit resourceBindings.js / deviceSlots.js
# Write audit log for important changes

h3. Connect new FeedFlow server

# Deploy new engine + volume
# Update WSAF_BRIDGE_URL and VITE_WSAF_BRIDGE_URL
# Update AMS_FRAME_ORIGINS on engine
# Redeploy AMS
# Reconnect all slots

h2. 16. Troubleshooting

| Problem | What to check |
| Website blank | Vercel deploy + env vars |
| Cannot login | Supabase keys + user is_active |
| FeedFlow offline | Railway health + bridge URL |
| Slot shows offline after redeploy | Manual reconnect |
| Cannot assign device | Device already has 2 accounts |
| Cannot use IP | IP inactive / flagged / already full |
| Ticket cannot go live | IP review not matched |
| Control Center numbers look wrong | Check account owner assignment |
