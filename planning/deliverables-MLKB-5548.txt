DELIVERABLES
------------

1. Centralized audit trail — one place to see who did what

   AMS records operational changes in a single audit store (audit_logs) with
   actor, timestamp, action type, entity, before/after values, and request context
   (IP and browser where available).

   | What is logged                         | Where operators see it        |
   |----------------------------------------|-------------------------------|
   | Account create, update, delete         | Audit Log page                |
   | Account status changes                 | Audit Log + Resource Ledger   |
   | Ban actions (manual / auto stage)      | Audit Log + Governance bans   |
   | Registration attempts (ok / fail)      | Audit Log + Register log tab  |
   | Prepared number add / remove           | Audit Log                   |
   | Device, SIM, IP ledger changes         | Audit Log                   |
   | Phone alignment fixes                  | Audit Log                   |
   | Ticket and IP-gate actions             | Audit Log                   |

   Audit Log screen (sidebar → Audit Log) supports filter by entity type and
   action type so supervisors can narrow down investigations.

2. Account activity history — status and assignment tracking

   Beyond the global audit log, AMS keeps structured history for accounts:

   | History type              | What it captures                          |
   |---------------------------|-------------------------------------------|
   | Status history            | Every status move: from → to, reason, who, when |
   | Device assignment history | Which device was linked and when it changed |
   | SIM assignment history    | SIM link/unlink over time                 |
   | IP / proxy history        | Proxy assignment changes over time        |

   Resource Ledger → account detail shows the full status timeline so operators
   and managers can trace how an account moved through the pipeline.

3. Mandatory registration activity log

   Every registration attempt must be logged — success or failure — before the
   workflow continues.

   | Field captured        | Why it matters                              |
   |-----------------------|---------------------------------------------|
   | Phone number & telco  | Identify which number was attempted         |
   | Site (MY / PP)        | Site-level reporting                        |
   | Result (ok / fail)    | Success rate tracking                       |
   | Fail reason           | Root-cause analysis when registration fails |
   | Device, proxy, operator | Accountability and troubleshooting        |

   Register page → Registration Log tab shows recent attempts. API exposes
   registration stats (success rate, fail reasons) used on Register and Governance.

4. Ban and recovery activity visibility

   Ban events are written to status history with stage (manual vs auto), reason,
   and source. Governance reads this data for operational reporting:

   | Report on Governance        | What leadership sees                     |
   |-----------------------------|------------------------------------------|
   | Ban rate by stage           | At Registration, Manual Nurture, Auto Nurture, In Use |
   | Ban causes & number segment | Top reasons and phone ranges             |
   | Bad IP flags                | IPs with repeated ban events             |
   | Recovery success rate       | Completed recoveries vs failures         |

   Recovery page tracks per-account recovery timeline (need → doing → ok / fail)
   stored on the account record for queue visibility and stats.

5. Operational monitoring surfaces — where teams see live workload

   | Screen              | Visibility purpose                                        |
   |---------------------|-----------------------------------------------------------|
   | Control Center      | Per-operator pending counts: link, nurture, scan, recover, tickets |
   | Register            | Badge for prepared numbers needing registration today; registration log |
   | Governance          | Supply levels, ban analytics, recovery, ticket processing |
   | Recovery            | Banned / recovering queue with status timeline            |
   | Tickets             | Delivery pipeline and reject reasons                      |
   | FeedFlow (bridge)   | Per-account feeding outcomes via feeding audit API        |

   Site switcher (All / Malaysia / Poipet) scopes counts and reports so managers
   can assess each market separately.

6. Assessment summary — framework status

   | Capability                         | Status   | Notes                                      |
   |------------------------------------|----------|--------------------------------------------|
   | Central audit write helper         | Complete | writeAudit used across API modules         |
   | Audit Log UI                       | Complete | Filterable table in AMS                    |
   | Account status history             | Complete | Drives bans reporting and ledger detail    |
   | Registration attempt logging       | Complete | Mandatory on every attempt                 |
   | Recovery timeline logging          | Complete | Per-account queue on Recovery page         |
   | Governance operational reporting   | Complete | Supply, bans, recovery, tickets            |
   | Control Center workload visibility | Complete | Operator task badges with site scope       |
   | Feeding session audit (FeedFlow)   | Complete | Bridge feeding audit + export CSV          |
   | RM supply diagnostic panel         | Complete | Governance only — feeds from logged data   |

   Gaps noted for future (out of scope for this assessment):
   - No single unified “activity feed” merging audit + status + feeding in one stream
   - Recovery log lives in account notes (structured JSON), not audit_logs table
   - Long-term retention / export policy for audit_logs not defined in AMS UI yet
